# 用 AI Agent 开发现有产品或代码库

修 bug、加功能、改性能或重构时，用这份指南。开始前，我要能描述用户期望的行为。结束时，我要能指出哪项证据证明这次改动有效。

## 1. 让 Agent 先建立基线

**我提供**：用户从哪里进入、输入了什么、现在发生什么、我希望发生什么。涉及性能时，补充数据规模、运行环境和衡量指标。

**我给 Agent 的指令**

> 任务是【目标】。先读适用的 `AGENTS.md`，找到用户真实入口、相关实现、现有测试和仓库通常使用的检查命令。沿入口追踪一次，再用具体输入说明现状。指出一个可能被改动影响的相邻行为。

| 任务 | 修改前我让 Agent 留下什么 |
| --- | --- |
| 修 bug | 最小复现步骤、实际结果和预期结果。若复现不了，记录试过的条件，并找能区分几种原因的下一项观察 |
| 加功能 | 当前最接近的用户路径、现有行为，以及新增后用户可见的差异 |
| 改性能 | 固定输入、环境和测量方法，记录基线，确保修改后能按同样条件比较 |
| 重构 | 记录要保留的外部行为，包括关键输出、错误处理或兼容性，用现有测试或样例固定它 |

## 2. 写好验收条件，再动代码

用一句话填空：**给定【起始状态】，用户执行【动作】后，从【可观察的位置】应看到【结果】。** 再选一个容易被破坏的边界情况。

例如：给定一批有 100 个不同订单号的订单，导出中途失败后，用户从原入口重试。打开最终文件，应得到恰好 100 个订单号，每个只出现一次。正常一次完成的导出也应保持原有结果。

让 Agent 沿用仓库中可靠的模式，完成满足验收条件的最小合理改动。对 bug，能自动重现时，把复现写成回归测试，先确认它在旧实现上会失败，再验证修复后通过。

## 3. 根据失败方式选择验证

| 我担心什么 | 我让 Agent 做什么 | 我看什么 |
| --- | --- | --- |
| 计算或数据错误 | 用已知输入跑测试，并通过真实入口生成结果 | 期望值与实际值、记录数、文件内容 |
| 用户操作没有生效 | 启动应用，走一遍功能地图中的用户路径；保存操作还要重开核对 | 截图或录屏展示操作，重新读取的状态证明结果持久化 |
| 模块各自通过，连起来却失败 | 运行相关集成测试，走过改动涉及的真实边界 | 请求、响应和最终写入或返回的结果 |
| 速度或资源消耗退化 | 在与基线相同的条件下重复测量 | 前后数值、波动范围和运行条件 |
| 重试、乱序等组合很多 | 先写出始终应成立的性质，例如“同一订单最多计入一次”，再用多种操作序列测试 | 实际覆盖的性质，失败时可复现的最小序列 |

如果功能难找，就补一行 **feature map（功能地图）**：功能名称 → 用户入口 → 操作步骤 → 成功证据。复杂协议若需要检查所有建模状态，可考虑 TLA+；有明确数学性质的算法可考虑 Lean。只有当问题确实需要这种保证时，再投入建模或证明的成本。

## 4. Review 时，把重复纠正放到合适的位置

先问：“哪项证据能证明用户的目标达成？”再看 diff 中风险最高的部分，例如数据如何写入、失败后如何恢复、旧数据是否兼容。遇到会再犯的问题，用下表决定该改什么。

| Review 时我发现…… | 我的动作 |
| --- | --- |
| Agent 找错入口、漏跑已有检查，或缺少做取舍所需的背景 | 更新 `AGENTS.md`，写明入口、准确命令和需要判断的条件。让新会话按说明重跑一次 |
| 错误能从代码结构直接识别，例如禁止某层跨边界导入 | 增加 lint 或依赖检查，给出可操作的报错信息，用违规和合法样例验证，然后接入已有检查流程 |
| 同一 API 容易被误用，连人也要反复推敲 | 简化接口或收紧类型，让正确用法容易表达。迁移旧例子，避免下一个 Agent 照抄 |
| 错误只有执行后才暴露 | 用最小复现补回归测试，确保修复前失败、修复后通过 |
| 代码里有解释临时补丁的注释，其他地方开始照抄 | 检查根因，清理误导性示例。必要的注释保留设计原因，可执行的约束交给代码或检查 |

## 5. 交付与上线分别验收

**合并前**，让 Agent 提交四样东西：行为变化、实际运行的命令及结果、能直接检查的产物、仍未覆盖的风险。对没有运行的检查，说明原因和它留下的未知项。我根据这些信息决定是否合并。

**涉及上线时**，从测试流程图里选与本次风险对应的动作。例如，部署时检查配置和集成；高影响变更先向少量用户发布，观察错误率；发布后用日志或真实用户指标确认预期效果。提前约定什么信号出现时应暂停或回退。发布动作按项目已有权限和流程执行。

### 一段可复用的任务提示词

> 在【项目】里完成【目标】。当前行为是【现状】，验收条件是【输入、操作、预期结果】，需要保持【相邻行为】。先读仓库说明，建立基线，再做最小合理改动。运行相关检查，从用户入口验证，并给我修改前后的证据、重跑方法和未覆盖项。若发现反复出现的问题，请指出最合适的长期修复位置，并说明怎样验证它有效。
