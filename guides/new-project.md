# 用 AI Agent 构思新产品或项目

当我有一个想法，还没决定该做什么时，用这份指南。目标是获得足够的证据，决定继续、改变方向或停止。如果值得继续，我手上还应该有一条跑得通的用户路径，可以作为后续开发的范例。

## 1. 先写清楚谁遇到了什么问题

**我来做**：挑一个具体的人和一次真实经历。写下对方想完成什么、现在怎样做、哪一步最费力，以及我亲眼见过什么。把其余判断标成假设。

**我给 Agent 的指令**

> 我观察到【用户】在【场景】下需要【结果】。上一次，他们用【现有做法】，遇到了【具体困难】。请整理出已知事实和待验证的假设，给出两个可行方案，并说明在什么情况下维持现有做法也合理。先停在方案阶段。

**我来判断**：哪一个假设一旦被推翻，会让我放弃这个想法？用它决定下一步该花时间做什么。

## 2. 为关键假设设计一个小实验

| 我想知道什么 | 让 Agent 帮我准备什么 | 我看什么证据 |
| --- | --- | --- |
| 用户是否真的需要这个结果？ | 用一份真实输入手工做出结果样例 | 目标用户是否把结果用进手头的工作，原流程中哪一步因此省掉了 |
| 用户能否自己完成操作？ | 只覆盖关键步骤的可点击原型和一个试用任务 | 观察用户能否在没有提示的情况下走完，卡在哪一步 |
| 技术上能否做到足够快、准或省？ | 使用代表性数据的小脚本，以及与现有做法一致的测量方法 | 核对输出，并比较耗时、错误数或单次成本 |

**动手前先写下决定标准。** 例如，我想做一个合并订单表的小工具。先拿上周两份真实格式的表，让一位每周做这件事的同事试用。约定成功意味着：对方能自行得到可交付的汇总表，订单数与人工核对一致，且能指出哪些重复订单需要处理。这次试用能回答关于这位用户的问题。要判断其他团队是否也需要，再找相应用户验证。

## 3. 决定写代码时，先打通一条用户路径

把第一版写成一条简短的 **feature map（功能地图）**。每行回答三个问题：有什么功能、用户从哪里进入、什么结果证明它有效。

| 功能 | 真实入口和动作 | 能证明成功的结果 |
| --- | --- | --- |
| 合并订单表 | 从导入页选择两份有重叠订单的样表，执行合并，下载文件 | 重新打开下载文件。每个订单号只有一行，合计与手工核对值一致 |

**我给 Agent 的指令**

> 只实现上表这条路径。先用样例说明预期输出，再实现并从用户入口跑一遍。交付时给我启动方法、实际输出和重跑验证的命令。把仍靠人工或模拟的步骤列出来，以便我决定原型能验证什么。

我亲自试一次，并查看决定成败的产物。导出功能要打开文件核对内容；交互是否容易理解要观察人使用；速度目标要用约定的数据量测量。

## 4. 原型值得继续时，整理 Agent 的工作环境

第一条可用路径会成为下一个 Agent 模仿的样例。把它整理清楚，并根据实际遇到的问题选择动作。

| 我遇到的情况 | 我采取的动作 | 怎样知道它起效了 |
| --- | --- | --- |
| 新 Agent 经常找不到启动方式、样表或验收入口 | 在仓库的 `AGENTS.md` 写下启动命令、检查命令、样表位置和功能地图入口；写明仍需人判断的产品取舍 | 换一个没有聊天上下文的 Agent，让它按文件说明复跑第一条路径 |
| Agent 总要猜应该调用哪个接口 | 收窄 API，提供一个正确用法，清理原型里会被误抄的临时实现 | 新功能能沿着现有接口完成；错误用法会被类型系统或接口拒绝 |
| 出现可由代码结构识别的重复错误，例如界面层直接导入存储模块 | 加一条范围明确的 lint 规则。报错中写清应使用哪个公共入口，把检查接进项目日常使用的命令 | 用一个违规样例确认会报错，用合法样例确认会通过 |
| 实际结果算错，例如重复订单被计入两次 | 保留最小输入和期望结果，写成自动测试 | 测试能在错误实现上失败，在修复后通过 |

把需要解释的设计原因写在最容易找到的位置。对机器能检查的约束，让 Agent 实际运行检查。对只用一次的探索，可以保留实验产物，等决定继续后再投入维护规则。

## 5. 做一次继续、调整或停止的决定

- **继续**：关键假设有证据支持。保存真实输入的可共享样例、验证方法和第一条可用路径，选下一条最有价值的路径。
- **调整**：记录用户在哪一步遇到什么问题，或哪项技术指标没达标。下一轮只改变影响该结论的部分。
- **停止**：记下哪个假设被推翻、依据是什么，保留足够信息供以后复查。
