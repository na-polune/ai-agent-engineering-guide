# AI Agent 编程实践指南

**先定验收条件，再让 Agent 动手。** 开工前问自己：“看到什么结果，我才会认为这件事做成了？”交付时，用同一条标准检查实际结果。

| 我现在要做什么？ | 从哪里开始？ |
| --- | --- |
| 我有一个产品或工具的想法，想判断它值不值得做。 | [构思新项目](guides/new-project.md) · 找出关键假设，设计最小实验，用结果决定下一步。 |
| 我需要在已有代码库里修 bug、加功能、改性能或重构。 | [开发已有项目](guides/existing-project.md) · 确认当前行为，写下验收条件，从用户入口验证改动。 |

## 怎样验证一次改动

以“导出中断后重试会产生重复订单”为例，我会这样分工：

1. **我定义成功。** 给定 100 个不同的订单号，中途失败后重试，最终文件应完整包含这 100 个订单号，每个恰好出现一次。如果“重试”和“重新导出”含义容易混淆，让 Agent 先画出失败后用户能做什么的状态图，我来确认它理解了需求。
2. **Agent 从真实入口验证。** 用同一批输入在旧版本复现，再在修复后从导出页重试。打开下载文件，将订单号与原始输入逐项核对。录屏能展示点击和重试过程，文件比对能发现漏单和重复。性能任务则用相同输入和环境比较前后测量值。
3. **我根据证据验收。** 让 Agent 交回输入、实际输出、重跑步骤，并说明哪些情况尚未覆盖。我检查这些证据是否回答了最初的问题，再决定是否合并。新项目也用这个原则：要判断用户是否会用，就观察目标用户亲自完成一次任务。

当风险来自许多不同的操作顺序时，可以让性质测试生成多种中断和重试序列，寻找违反“订单不重不漏”的反例。若需要验证协议在给定假设下的所有建模状态，再考虑用 TLA+ 做模型检查。[Tan 讲运行验证与形式化验证](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=580s)

## 让下一次验证更容易

- **让 Agent 找得到，也跑得起来。** 对反复验证的功能，记录用户入口、操作和成功证据，形成一张功能地图。把稳定的操作封装成可重跑的命令，在 `AGENTS.md` 写清入口和运行方法。[功能地图与验证工具](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=580s)
- **把重复的审查意见变成仓库里的改动。** 接口容易用错，就收紧 API。模块频繁越界，就加 lint 规则，在报错中写明正确入口，再清理会被照抄的旧例子。像重复订单这样的行为错误，则把复现用例保留为回归测试。[代码库与可执行约束](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=123s)
- **先跑通一次，再扩大自动化。** 当单个 Agent 能稳定复现、修复并验证同类问题后，再把流程用于并行任务或每次发布。扩大规模时，也要跟踪用户实际感受到的指标，例如启动耗时、输入延迟或导出错误率。[用户体验指标](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=812s) · [发布自动化](https://www.youtube.com/watch?v=O_zcc6Xl12g&t=911s)
